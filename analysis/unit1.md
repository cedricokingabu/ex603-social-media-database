1. Modeling Justification
   The choice of SERIAL primary keys reflects deliberate optimization for this social media platform's expected usage patterns. Auto-incrementing integers provide superior performance characteristics compared to UUID alternatives: they consume 4 bytes per key versus 16 bytes for UUID, resulting in significantly smaller index sizes and faster query execution. Sequential IDs naturally support database sharding by partition ranges, enabling horizontal scaling as the platform grows.
  Additionally, the use of SERIAL keys simplifies the implementation of foreign key relationships, as they are straightforward to reference and maintain. This design choice enhances data integrity and consistency across related tables, ensuring that relationships between users, posts, likes, dwell times, and hashtags are efficiently managed. Overall, the adoption of SERIAL primary keys aligns with best practices for high-performance database design in social media applications.
   On Delete Cascade Justification
  Cascade deletes are schema-enforced rather than application-managed because data consistency is non-negotiable in relational databases. When a user deletes their account, all downstream data must be removed atomically: their posts, likes on other posts, dwell-time records, and post-hashtag associations. Enforcing this at the schema level guarantees referential integrity regardless of application bugs or developer oversight. We enforced this schema oriented approch because on the application approach if a developer forgot to remove a record it will create an orphan which will violate ACID property.
  Unique Constraints: The UNIQUE(user_id, post_id) composite key in the likes table prevents users from liking the same post twice. This is a business rule that cannot tolerate race conditions or application bugs. By enforcing at the database level, concurrent requests from the same user (e.g., double-clicking a like button) are serialized—the second request fails with a constraint violation, which the application catches and handles gracefully.
  Soft Deletes (is_deleted flag): Posts and users can be marked deleted without cascade-removing dependent records. This allows recovery, preserves historical data, and enables compliance audits. The application decides whether to show deleted posts in queries (WHERE is_deleted = FALSE). This flexibility is intentional—if requirements change to permanently delete after 30 days, we add a cleanup job without schema changes.
  Edit Tracking (is_edited flag): The database records the flag, but application logic determines why a post was edited (typo vs. misinformation). This is a business concern, not a data constraint.
  This schema prioritizes atomic consistency and performance by enforcing immutable structural rules (PKs, FKs, uniqueness) at the database level, while reserving flexibility for business logic (moderation, soft deletes, engagement metrics) in the application. This separation of concerns makes the system robust, auditable, and maintainable as requirements evolve.

2.Reflection
  The requirements didn't specify how to associate posts with hashtags. I chose a normalized many-to-many relationship via the POST_HASHTAGS junction table, but a different designer could reasonably have denormalized hashtags directly onto posts as a PostgreSQL ARRAY or TEXT field.The junction table optimizes for the platform's dominant access pattern (hashtag discovery), while accepting marginally higher write latency when posts are created. 
  The other decision that was made is not to add a comment table as it was not specified as one of the user. But it makes really sense to have a comment table. I also though of living it out since this is a class project and in real life for applications like Tinder we dont have comments but only likes and hashtags. So the emphasis on adding a comment table was not really evident.
